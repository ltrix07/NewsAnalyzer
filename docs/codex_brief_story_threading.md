# Codex brief — Story threading (reply-updates at delivery)

## Goal

Multi-day stories (e.g. a Russian strike on Kyiv whose casualty toll updates over 2–3
days) currently arrive as several separate top-level Telegram posts. The within-run
`consolidate` stage only merges fragments created in the SAME pipeline run, so a
next-day update ("В Киеве 19 погибших", a new event) cannot merge with yesterday's
already-filtered event and posts fresh. Confirmed from production: three 6-July Kyiv
events + one 7-July update all delivered as distinct posts.

Fix at delivery: when a pending digest is an **update to a story already delivered**,
send it as a **Telegram reply** to that story's previous message (threaded), instead of a
new top-level post. The user still gets the details — quietly nested under the original —
rather than repeated top-level spam.

Product decisions (already made, implement exactly):
- **Update content = the full digest** (normal `format_digest` output), prefixed with an
  update header. No delta-summary LLM call in v1.
- **Updates are silent**: reply sends use `disable_notification=True`. The story's first
  (top-level) post notifies normally.

## Non-goals

- Do NOT remove or weaken the within-run `consolidate` stage. It stays (cuts gpt-4o cost
  by merging same-run fragments before verify/summarize). Threading handles the
  cross-run/cross-day case; they are complementary.
- Do NOT do theme-level grouping (e.g. two different UA–PL statements). Threading uses the
  strict "same underlying event" definition (same incident / updated tolls / adjacent
  districts = same; different city or different incident = NOT same). This keeps a Kharkiv
  strike from threading under a Kyiv strike.
- Do NOT suppress/drop updates. Every update is delivered, just threaded and silent.

## Schema change (migration required)

Add one nullable column to `digests`:

```python
telegram_message_id: Mapped[int | None] = mapped_column(BigInteger, nullable=True)
```

Generate an Alembic migration (`make db.revision name="digests_telegram_message_id"`,
then review the autogenerated file). **This feature needs `alembic upgrade head` on
deploy** — call it out in the PR description; a git-pull without the migration will leave
`telegram_message_id` missing and break delivery (this exact class of miss took delivery
down before).

## Client change (`delivery/client.py`)

`TelegramBotClient.send_message` already returns the full parsed Telegram JSON
(`{"ok": true, "result": {"message_id": ...}}`). Add two optional params, threaded into
the request body only when set:

```python
reply_to_message_id: int | None = None,
disable_notification: bool = False,
```

Map `reply_to_message_id` and `disable_notification` into `body`. No other change.

## Config (`engine/config.py`)

```python
thread_updates_enabled: bool = True
thread_window_hours: int = 72
thread_min_similarity: float = 0.50
thread_max_candidates: int = 3
```

Reuse `openai_model_consolidate` (gpt-4o-mini) for adjudication. When
`thread_updates_enabled` is False, every digest is sent as a normal top-level post (no
parent lookup, no adjudication).

## Shared adjudication helper (light refactor)

The pair-adjudication logic currently lives inside `engine/cli/consolidate.py`
(`_load_compact_event_articles`, `_llm_adjudicate_pair`, `PairJudgement`, the
`SameEventVerdict` + `consolidate_v1.j2` call). Factor the reusable part into a shared
module (e.g. `engine/consolidation_match.py`) exposing:

- `async def same_event(session, event_a: Event, event_b: Event, *, settings) -> PairJudgement`
  (renders `consolidate_v1.j2` over each event's compact articles via
  `load_event_articles(session, event_id, limit=3)`, calls the mini model, returns the
  verdict + token/cost accounting).

Import it from both `engine/cli/consolidate.py` (behavior unchanged — existing
`tests/test_consolidate.py` must still pass) and the dispatcher. Keep the adjudicator
**injectable** so tests supply a deterministic fake.

## Delivery logic (`delivery/dispatcher.py`)

Make `deliver_pending` accept optional injectables with defaults (so the CLI is
unaffected and tests can substitute fakes):

```python
async def deliver_pending(
    limit: int | None = None,
    *,
    client: TelegramBotClient | None = None,
    adjudicator: Adjudicator | None = None,
) -> DeliveryReport:
```

Inside the existing ranked send loop, for each pending digest:

1. **Find a parent** (only if `thread_updates_enabled`): call a new
   `_find_thread_parent(session, digest_model, settings, adjudicator)`:
   - Load this digest's event centroid.
   - Query delivered digests where `delivered_at >= now() - thread_window_hours`,
     `telegram_message_id IS NOT NULL`, `event_id != this.event_id`, joined to their
     events, with centroid cosine similarity `>= thread_min_similarity`; order by
     similarity desc, take up to `thread_max_candidates`.
     (Use pgvector `Event.centroid.cosine_distance(vector)`, `similarity = 1 - distance`,
     like `engine/cli/consolidate.py:_candidate_pairs`.)
   - Adjudicate candidates with the injected `same_event` adjudicator; the FIRST candidate
     confirmed `same_event=True`, ordered by **most recent `delivered_at`** (chain to the
     latest message in the thread, not the root), becomes the parent. Return its
     `telegram_message_id` (and headline, for the header).
   - Note: because we `flush()` after each send in the loop, a digest delivered earlier in
     THIS same run is a valid parent — so intra-run same-story fragments that consolidate
     missed also thread correctly.
2. **Send:**
   - Parent found → prepend an update header and send as a silent reply:
     ```
     header = f"🔄 <b>Обновление по теме:</b> {html.escape(parent_headline)}\n\n"
     await client.send_message(
         chat_id, header + message,
         reply_markup=build_digest_keyboard(digest_model.id),
         reply_to_message_id=parent_message_id,
         disable_notification=True,
     )
     ```
   - No parent → normal send as today (notification on).
   - Keep the 👍/👎/💬 keyboard on updates too (they must stay ratable).
3. **Capture message_id:** from the send response, `digest_model.telegram_message_id =
   response["result"]["message_id"]`. Do this for BOTH reply and normal sends, so later
   updates can chain.
4. **Impression:** log as today; add `"threaded_parent_digest_id"` (int | None) into the
   impression `context` for later analysis.

### Failure handling

- If a reply send fails specifically because the reply target no longer exists (Telegram
  error like "message to be replied not found" / "message to reply not found"), retry
  once as a **normal top-level send** (notification on, no `reply_to_message_id`). Other
  errors keep the existing behavior (count `failed`, log, continue — do not mark
  delivered).
- A parent whose `telegram_message_id` is NULL (delivered before this feature) is simply
  not a candidate (query filters `telegram_message_id IS NOT NULL`) → digest sends
  top-level.

## Optional companion tweak (only if trivial)

Lower `consolidate_candidate_min_similarity` default `0.60 → 0.50` so same-run
near-duplicates at least reach the adjudicator. The adjudicator still gates precision. Do
NOT change the strict prompt. Skip if it destabilizes `tests/test_consolidate.py`.

## Tests (`tests/`, follow existing delivery test style)

Inject a fake `TelegramBotClient` that records each `send_message` call's kwargs and
returns `{"ok": True, "result": {"message_id": <incrementing>}}`, and a deterministic
fake adjudicator.

1. **Threads an update:** a delivered digest (event A, `telegram_message_id` set) + a
   pending digest (event B, adjudicator returns same) within window → B sent with
   `reply_to_message_id == A.telegram_message_id` and `disable_notification=True`;
   `B.telegram_message_id` stored.
2. **Top-level when unrelated:** adjudicator returns not-same (e.g. Kharkiv vs Kyiv) → no
   `reply_to_message_id`, notification on.
3. **Chain to latest:** A delivered, update1 threads under A, update2 threads under
   **update1** (most recent), not A.
4. **Pre-feature parent:** candidate with `telegram_message_id IS NULL` is ignored →
   top-level send.
5. **Reply-target-missing fallback:** fake client raises the "reply not found" error on
   the reply attempt → digest is retried and sent top-level, marked delivered.
6. **Disabled flag:** `thread_updates_enabled=False` → never calls adjudicator, all
   top-level.
7. **Window bound:** a same-story parent delivered older than `thread_window_hours` is not
   used → top-level.

No live OpenAI or Telegram calls in tests.

## Acceptance criteria

- Multi-day story: first post top-level (notifies); subsequent updates arrive as silent
  replies threaded under the most recent message of that story, carrying the full digest +
  feedback buttons.
- Different cities / unrelated events never thread together.
- `make lint` and `make test` pass; existing `tests/test_consolidate.py` still green after
  the adjudicator refactor.
- `thread_updates_enabled=False` fully reverts to current top-level behavior.
- PR description explicitly states `alembic upgrade head` is required on deploy.
